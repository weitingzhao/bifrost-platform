# Ops Console 业务说明（给 Design）

> 2026-10-21 起草，供 Claude Design「Bifrost Ops Console」项目优化 ops.bifrost.lan 使用。
> 本文只讲**业务**：谁在用、为什么用、每次来要回答什么问题、要做哪些决定。视觉与组件规范仍以同目录 `README.md`、`guidelines/` 为准；两者冲突时，以本文的业务优先。
> 本目录 `README.md` 写于 2026-09-11，那时这个界面还是「运维监控台」。2026-10-16 起定位已经变了（见第 1 节），README 里关于 Massive 等插件页的写法只适用于 System 下面的详情页。

---

## 1. 一句话定位

**ops.bifrost.lan 是 Owner 指挥一支 AI Agent 施工队、看住家里这套系统的驾驶舱。**

它不是给运维工程师盯曲线的监控台。打开它的人只有一个，他要的是：

- 有没有**要我做**的事？做完就走。
- 活**在动**吗？没卡、没坏，我就放心。
- 我想让 Agent **做件事**，在哪说？

## 2. 谁在用、在哪用、怎么用

| | |
|---|---|
| 用户 | **只有一个人：Owner**（系统所有者）。他的太太用 Trade（trader.bifrost.lan）交易，不用 Ops。 |
| 设备 | **手机最多**（批单、答问题、看进展、叫停），其次电脑，平板偶尔。 |
| 节奏 | 一天打开很多次，每次几十秒到几分钟，多是碎片时间；发版和出事时要快、要准。 |
| 身份 | 用管理员令牌登录才能批、答、签；没登录时只读。 |
| 语言 | Owner 用中文思考和交流。现行规则是界面文字用英文；Agent 写的内容（计划步骤、参谋长的话、目标）是中文。见第 10 节「待定」。 |

## 3. 业务背景：为什么有这个界面

**家里的几套产品**：Trade（太太交易 Owner 的股票和期权账户）、Finance（家庭流水与预算）、以后还有别的家庭项目。它们业务各自独立。

**谁在建、谁在维护**：一支 AI Agent 施工队，Owner 给它起名 **Bifrost Crew / 小牛牛包工队**。Agent 写代码、过测试、互相复核、发版、运维。Ops 平台是它们的工地和调度台，也是 Owner 看住这一切的地方。

**Owner 是唯一的人，也是整个体系的瓶颈。** 这个界面的全部价值，在于让他只做该他做的事，其余的一眼就能确认「在动、没卡、没坏」，不用读日志、不用问人。

用包工队来比喻（Owner 认可这套说法，界面文案可以借用）：

| 包工队 | 在系统里 | 界面上 |
|---|---|---|
| 业主 / 甲方 | Owner | 唯一的用户 |
| 工头 | 参谋长（chief of staff，一个 Agent 岗位） | Chief 入口：和他对话、给他目标 |
| 工人 / 分包 | 执行者：Codex、Cursor、Claude 等不同厂商的 Agent | Work 里的 Crew、尝试（attempt） |
| 监理 / 质检 | 确定性验收（门槛、测试）+ 独立复核（作者≠复核人） | 计划里的「门槛」「复核」步骤 |
| 施工合同 / 授权书 | 常备授权规则（哪些事 Agent 自己能做，放宽要 Owner 签） | 审批单的等级 B / C / D |
| 工棚 | Agent 主机（ubt-k3s-06） | Crew 卡片里的 host |
| 交房 | 代码进 main、发版上 PROD | Releases、审批单 |
| 禁区 / 电闸 | **D10：实盘交易冻结**，任何 Agent 都不能下单 | 界面上没有任何下单动作，也不能有 |

和真包工队不同的两点，设计时别盖住：
- 工人每次都是新来的、不带记忆，全靠任务书和记录，所以「记录」「谁做的、依据什么」很重要，但它们属于详情，不该占首屏。
- 工头管不了钱和合同：放宽规则、PROD 发布只有 Owner 能批。

## 4. Owner 只做三类事

这是整个设计的出发点（架构决策 ADR §1）：

1. **定目标**：告诉参谋长要做成什么。
2. **定规则**：签授权规则、批准放宽、任命岗位。
3. **不可逆的事**：PROD 发布、删除数据或备份、密钥、钱和交易。

对应到界面上，他会做的动作只有这些：

| 动作 | 现在在哪 | 说明 |
|---|---|---|
| 批 / 拒审批单 | `#approvals?id=…`（从 For you 进） | C 级：批了马上执行；D 级：批了以后还要在终端跑一条命令（界面给出可复制的命令）；B 级不用批。 |
| 回答 Agent 的问题卡 | `#questions?id=…` | 几个选项，其中一个标「推荐」；可以选「都不是」自己写。**答问题不等于批准**任何发布或改动。 |
| 签收计划步骤 | Work › 计划区顶部「Waiting for your sign-off」 | 每步带编号（如 `2.4-1`），一行一个「Sign off」，确认后消失。 |
| 给 Agent 一个目标 | Chief › 「Give the agents a goal」 | 一段话 + 选仓库，提交后得到一个目标编号 M-n。 |
| 和参谋长说话 | Chief › 对话 | 文字或语音输入。 |
| 叫停全部 / 恢复 | For you › 「Work control」 | 停的是 Agent 的活，不是交易。现在只在 STG 开放。 |
| 在终端跑一条命令 | 审批单、问题卡里给出 | 只有他的权限能做的集群写操作；界面要给可复制、原样能跑的命令。 |

**不属于这三类的事，一律不该推到他面前。** Agent 能自己判断、自己做、自己恢复的，界面只需要让他看见结果，不需要他点。

## 5. 他每次打开要回答的问题（按阅读顺序）

页面应当按这些问题组织，而不是按系统怎么搭的来排面板。每个问题都已有接口算好的答案，界面只负责呈现，不在前端重新判断。

**Q1 有没有要我做的？**（For you）
- 几件？最急的是哪件？点一下直接到能做决定的地方。
- 全站只有**一个**「要你做」的数，一个口径。现在计入：待批的审批单、批了但要他去终端跑的、状态不明需要他确认的、没答的问题、丢失的 Agent 主机、运行时的「需要你」卡片、IB 网关掉线（要他登录 TWS）。不计入：静默的线程、演练、计划签收、发布策略到期。
- 读不全时，数字显示「?」而不是 0。**没读到不等于没有。**

**Q2 活在动吗？**（Work）
- 现在谁在做什么？有没有卡住的？
- 这一轮还差多少？（例如「第 2 轮 72/75 步」，按组看：2.3 交互总线与叫停 5/7）
- 下一步轮到谁：Owner、Agent，还是统筹？
- 有没有需要我签收的步骤？

**Q3 机器好吗？**（System）
- 健康：有没有红灯？
- 发布通道：空闲还是被谁占着，STG 和 PROD 各跑的是哪个版本。
- Agent 主机、集群节点、数据（行情、券商对账单、研究批处理、备份）、额度（各厂商 Agent 用了多少）。

**Q4 我想让 Agent 做件事、问一句。**（Chief）

## 6. 四个入口与详情页

2026-10-16 Owner 采纳的结构：**一级入口只有四个**，其他都是从 System 或单据进入的详情页，不再加一级入口。

| 入口 | 回答 | 现在有什么 |
|---|---|---|
| **For you**（首页） | 有没有我的事？ | 结论横幅（「Nothing needs you」/「1 thing is yours」）、叫停与恢复、Yours 列表（待签收入口、待办行、「下次需要你」、最近处理）、Worth a look（值得一看的告警，可一键变成目标） |
| **Chief** | 我要说、我要派活 | 和参谋长的对话、给 Agent 一个目标、参谋长最近写了什么做了什么 |
| **Work** | 活在动吗？ | Now（在跑 / 卡住 / 开着的目标）、开着的目标、Crew（主机在线）、额度、**计划卡片「The plan · Round N」**、目标卡片（目标→计划→实现→验收→复核→完成）、概览、**计划区**（签收、各组步骤、架构对照）、主机、历史、提交血缘、代码健康 |
| **System** | 机器好吗？ | 健康、发布通道、额度、能力分数、节点、数据各块 |

详情页（从 System 底部或「⋯ 更多」进入）：Status、Data（行情 Massive、券商对账 IB Flex、研究引擎、备份）、IB（交易网关）、Releases（STG/PROD 版本、进行中、历史、回滚申请）、Infrastructure（集群、网络、Mac mini）、Records（关闭的、工作、审计、巡检）。

单据页（没有导航行，只从链接进）：审批单 `#approvals?id=`、问题卡 `#questions?id=`。

三种设备三种导航（已定）：手机和平板竖屏用底部 4 个 tab；平板横屏用窄图标栏；电脑用侧栏（4 个入口 + 可折叠的「Detail pages」）。

## 7. 业务名词（Design 要认得的）

| 名词 | 意思 | 例子 |
|---|---|---|
| 目标 goal / mission | Owner 或参谋长定的一件要做成的事 | `M-38` |
| 任务 task / 尝试 attempt | 目标拆出来的一件活；一次执行叫一次尝试，可能重试 | `t_01M5…/a1` |
| 计划 plan | 轮 → 项 → 步，三层；每步有编号 | 第 2 轮 → `2.3 交互总线与叫停` → `2.3-4（补强）独立复核` |
| 步骤状态 | 进行中 / 已完成 / 未开始；「manual」表示由台账导入或人工记录完成的步 | `2.3 · 5/7 · 3 manual` |
| 签收 sign-off | Owner 确认一步做完了；只有他能签 | 「Waiting for your sign-off · 10」 |
| 架构对照 | 设计里每一行能力，是否有门槛证明它真的成立 | 17 行：13 passed、4 no gate yet |
| 门槛 gate | 发版后自动跑的检查批次 | `M-104 … {"accepted": 13}` |
| 审批单 | 要 Owner 批的动作，带编号、等级、「批了会发生什么」「没做的检查」「出错怎么回退」 | `#82 · tier C · bifrost-deliver-platform-prod @ b6b565f` |
| 问题卡 | Agent 问 Owner 的选择题 | Q22 |
| 环境 STG / PROD | 测试环境 / 正式环境；**各有一份计划和数据** | stg.ops.bifrost.lan / ops.bifrost.lan |
| 发布窗口 | 同一时间只允许一个发布；被占时别的发布排队 | 「Held by … for bifrost-platform」 |
| 额度 quota | 各厂商 Agent 的用量池 | claude weekly 56% |
| 叫停 stop all | 停掉所有 Agent 的活 | |
| D10 | 实盘交易冻结，硬边界 | |

## 8. 状态与颜色

- **颜色只表示严重程度**：绿＝正常，黄＝需要看一眼，红＝坏了要处理，灰＝读不到 / 判断不了，蓝＝提示。
- **不借用交易的红涨绿跌**：这里的红是「坏了」，不是「跌了」。
- **加载中、读失败、真的为零，三者要分得开**。曾出现过加载态被看成「0」的误判。
- 页头一行总状态：All clear / Degraded / Failing / Unknown。

## 9. 已定的设计原则（Owner 的原话和决定）

1. **业务优先**：设计美观和业务能力冲突时，业务赢。有数据、能回答这页业务问题的，就要放上页面；设计只定位置和形态。
2. **主次有序，复杂性收进 Detail**（10-16）：首页每块先回答三件事：要不要他出手、是谁的事、下一步是什么。事件流水、来源、id、关系图放进详情，不删。
3. **按业务问题组织，不按组件**：先列这页主人要回答的 3–5 个问题，按阅读顺序排，再决定每个问题用哪个已算好的判定回答。
4. **每页三幕**：先结论，再内容，后操作。核心操作永远看得见，不藏在折叠里。
5. **一个数，一个口径**：全站「要你做」只有一个数。
6. **按钮只放决定或请求**，不替他陈述事实（不能有「我已经做完 X」这类按钮）。
7. **说清楚「是什么、为什么是你、不做会怎样」**，不用内部说法。
8. **手机优先**：触控目标 ≥44px，不横向滚动。
9. **设计里没有，不等于该删**：删除由统筹判断并留档。

## 10. Owner 已经说过的问题（这一轮设计的输入）

都来自 2026-10-21 他实际使用时的反馈：

| # | 问题 | 原话或现象 |
|---|---|---|
| 1 | 「Plan ›」点了没反应 | 「我点了Plan后，没反应，感觉Ops 目前的交互还是很烂啊」。已在 Work 页时只改了地址；第二次点地址不变就完全不动；吸顶页头可能遮住目标。三个「Goals ›」同样。 |
| 2 | 计划里找不到要签的步骤 | 「这些编号根本就没有明确的规范，高亮……这个页面根本没有达到可用的级别」。已补编号徽标和顶部签收区，Design 时整体再看。 |
| 3 | STG 和 PROD 分不清 | 他在 STG 上签了 4 步，以为生效了；两边各有一份计划。**环境必须非常醒目**，尤其在要他做决定的地方。 |
| 4 | 「计划」「这一轮」希望是中文 | 「这两部分到了Ops 后也希望可以保持中文」。与全站界面用英文的规则冲突，**待定**：这一轮设计里定全站的语言策略。 |
| 5 | 同一个数两种颜色 | 「要你做」的数字徽标是红的，横幅是黄的。 |
| 6 | 横幅说「See them ›」，但内容是「Nothing needs you」 | |
| 7 | 签收等待排在 Yours 第一行，却不计入「要你做」的数 | 口径不一致。 |
| 8 | 重复 | 额度出现 3 处，架构计数 3 处，主机 2 处，For you 上的等待项 2 处，发布审批在 For you 和 Releases 各一处。 |
| 9 | 审批单里「Plan step」链接到计划顶部，不是那一步 | 已完成的步骤还收在折叠里。 |
| 10 | 原始字段直接露出来 | 例如主机列表里的「Online: true」。 |

## 11. 边界（设计不要越过）

- **Ops 永远不了解交易业务**：Greeks、券商协议、具体策略都不在这里。Trade 的界面另有设计体系（Bifrost Dense UI），两边不共用颜色语义。
- **没有任何下单、实盘交易的入口**（D10）。「叫停」只停 Agent。
- **集群写操作不在界面上直接执行**：界面发起申请（审批单），批准后由平台执行，或给出命令让 Owner 在终端跑。
- 本文说的是 Owner 一个人的驾驶舱。以后接入家里别的产品时，入口结构不变，产品作为「目标」和「数据」的来源出现。

## 12. 希望这一轮设计交付什么

1. **三类关键屏**，每类出手机稿和电脑稿：
   - For you（首页）
   - Work，含计划卡片、计划区和签收
   - 单据页：审批单、问题卡
2. **用真实数据的形状**画（接口见下），不要用自编的理想数据：计划步骤标题很长，而且是中文；审批单的理由有好几段。
3. 第 10 节每一条要么在稿子里解决，要么写明为什么不解决。
4. 新组件进 Ops 设计系统 v2（https://claude.ai/artifact/WAXPKFjtR85QrcCutX1rYc）。

数据来源（都在 platform-api `/api/v1/` 下）：
- `approvals?status=open|all`、`questions?status=all`
- `agentrt/progress`、`agentrt/plan?root=R2`、`agentrt/events?stream=plan:R2`
- `agentrt/missions`、`agentrt/tasks`、`agentrt/pools`
- `agentrt/messages/thread?with=seat:chief_of_staff`
- `telemetry/alerts`、`cluster/nodes`、`delivery/release-window`、`releases`

代码位置：`console/src/lib/shell/consoleRoutes.ts`（入口与路由）、`console/src/pages/shell/owner/`（四个入口）、`console/src/pages/shell/agents/`（计划与签收）、`console/src/pages/ApprovalsPage.tsx`、`console/src/pages/question/`。
